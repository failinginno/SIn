# SINGULAR Native BNB V1 Threat Model

This is an engineering review of the local V1 design, not an independent audit. The trust boundary is the deployed pool manager, its configured randomness provider, BNB recipients and the owner accounts.

| Threat | Control in V1 | Residual risk / follow-up |
|---|---|---|
| Reentrancy from winner, refund recipient or fee recipient | Effects precede low-level BNB transfer; claim, refund, fee sweep and vault withdrawal use OpenZeppelin `nonReentrant`. | Receiver can intentionally reject payment, retaining but delaying its own claim. |
| Overselling / stale frontend state | Contract enforces `quantity <= capacity - entriesSold` and exact `msg.value`; final purchase atomically closes entry. | Frontend must surface revert and refresh chain state. |
| Deadline boundary / validator timestamp | Entry rejects at `block.timestamp >= deadline`; refunds work at the same boundary. | A validator can slightly influence timestamp near the boundary. Communicate the chain's authoritative deadline. |
| Randomness manipulation | Winner is derived only from `randomValue % capacity` and recorded ticket owner. Callback requires the stored provider and request. | Provider trust is critical. Mock owner can choose the value. A production provider must be independently evaluated before launch. Modulo bias may exist for bounded random domains; a sufficiently uniform 256-bit value makes it negligible for capacity ≤ 500. |
| Reroll / duplicate callback | Request becomes consumed and the winner is stored once before claims. No second random request or owner winner setter exists. | A VRF response at or after the fixed 6-hour timeout is ignored; users refund instead. Transaction ordering at the timeout boundary determines which state is final. |
| Admin abuse | Constructor-fixed creator can create new pools only; constructor-fixed fee recipient can withdraw realized vault fees to itself only. No pause, ownership transfer, pool-economics setter, ticket editor, winner selector, active-pool cancellation, provider setter or participant-fund withdrawal. | Creator can create new pools with different disclosed economics. A separate new deployment is possible; users must verify the contract address. Losing a fixed key cannot be repaired in place. |
| Forced BNB | Accounting exposes excess BNB; fee vault only credits manager calls. | Forced excess is not owner-withdrawable and may remain locked. |
| Failed native transfer | Revert restores claim state; original winner or refund entitlement stays fixed. | A permanently rejecting recipient cannot redirect payout in V1. |
| Double claim | `prizeClaimed`, `refundClaimed` and `feeSwept` set before transfer; all paths reject repetition. | Review again after any future contract change. |
| Asset/liability mismatch | Four tracked liabilities sum to manager BNB balance in normal flows; invariants test randomized sequences. Fees sweep only after outcome. | Unexpected forced BNB creates positive unaccounted balance; no mechanism covers a real deficit. |
| Provider denial of service | Final purchase reverts atomically if request fails; the provider cannot be replaced after deployment. A fulfilled request resolves before the timeout; afterward any user can claim a full refund. | A recipient contract that refuses BNB can still make its own refund unclaimable. VRF billing and callback gas require monitoring. |
| Automatic renewal | A recurring pool renews once only after successful VRF fulfillment. Expiry and VRF timeout convert contributions to refunds but do not create a new pool. | The creator must manually replace expired pools. A clock cannot trigger a transaction. A `WAITING` pool without any purchase never expires. |
| Flap interaction custody | `buyEntriesFor` records the real beneficiary, and permissionless claim-for methods only pay the recorded rights holder. The Flap Vault forwards ticket BNB directly and tracks tax revenue separately. | Users must enter exact BNB value in Flap's generic form; the live Flap UI and Portal have not yet been tested. Flap Guardian can invoke the factory's restricted vault-creation method, but has no manager privileges. |
| Gas exhaustion | Capacity capped at 500; test measures max-batch gas. | A 500-entry purchase costs roughly 13.4 million gas locally; verify BSC transaction gas limits and consider a lower cap or more compact ticket ledger. |
| Event / indexer inconsistency | State is authoritative; events expose pool, buyer, request and settlement identifiers. | Indexers must handle optional expiry sync and chain reorganizations. |

The owner has no direct route to participant BNB, but choosing a malicious provider at deployment can bias outcomes. Do not claim the project is trustless or verifiably random until the deployed provider, coordinator and verified bytecode are independently checked. This is not an independent audit.
