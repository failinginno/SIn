## Completed locally

- Pool creator can only create new pools. The address is immutable; there is no pause, owner transfer, provider setter, winner setter, manager withdrawal, or upgrade selector.
- Fee recipient is immutable. The manager sends only realized fees from completed pools to a separate fee vault; `withdraw(uint256)` can only pay this recipient and cannot exceed `availableFees`.
- `buyEntriesFor` records the beneficiary as the ticket owner and contributor; `claimPrizeFor` / `claimRefundFor` are permissionless triggers that pay the original rights holder directly, never the trigger or Flap Vault.
- `SingularFlapVault` exposes Flap VaultBaseV3 discovery and a UI schema for pool reads, exact-value BNB purchase, prize/refund claims, and token-tax-revenue actions. User ticket funds are forwarded immediately to the independent pool manager. Native tax revenue uses balance-delta accounting and a fixed payout address.
- `SingularFlapVaultFactory` exposes the v2.3 factory discovery/validation surface for a native-BNB quote and one official token vault. Its restricted `newVault` permits the official Flap VaultPortal or Guardian, as the Flap specification requires. Neither receives pool-manager authority.
- `forge test --profile ci`: 44 tests passed, 0 failed; 65,536 invariant handler calls with 0 reverts. `npm test`: 16 passed.

## Not yet verified / release blockers

1. The BSC Testnet VRF provider, manager, fee vault, and Flap Vault factory were deployed by the owner via MetaMask on 2026-10-05 (details below). No Flap token or vault deployment has been made from this version. The Flap Portal and generated interaction page have **not** been exercised with a real wallet.
2. The local Flap discovery surface follows the current published interface, but the official Flap spec checker and a live VaultPortal call have not yet passed. Do not claim Flap compatibility or show a working Flap purchase CTA until they do.
3. Flap's optional low-risk badge currently requires a Guardian-controlled upgradeable beacon and partner audit. This project deliberately keeps user-fund custody in an immutable, separate manager. Its immutable Flap Vault is not eligible for that badge under the current rule.
4. The Flap Guardian can invoke the factory's restricted vault-creation function. This is a platform-spec permission, not a pool-manager permission. Local factory logic now reserves the `officialVault`/`officialTaxToken` slot for the canonical VaultPortal only, so a Guardian backup call cannot consume it; a regression test covers Guardian-before-Portal ordering. This remains a platform trust boundary and needs live Portal testing.
   Plain BNB sent to the Flap Vault without `buyEntries` counts as tax/donation revenue and can be released to the fixed tax recipient. The live UI must warn users not to send ticket payments directly to the Vault address.
5. A permanently unavailable VRF callback can leave a full pool in `DRAWING`; no administrator rescue or reroll path exists. The subscription owner can also remove a consumer or stop funding, which is a liveness risk (not a winner-selection power). The happy-path draw and refund have now been observed, but callback failure behavior, subscription depletion, and adversarial claims still lack live Testnet evidence.
6. The current working directory is not a Git repository, so tracked-secret and source-commit checks cannot yet be completed. No signing secret may enter source, frontend variables, command history, or this report.
7. Independent smart-contract audit, legal/regulatory review for paid prize draws, live explorer source verification, onchain asset/liability reconciliation, and actual Flap UI testing are still required before mainnet.
